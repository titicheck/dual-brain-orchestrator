# Orchestrator V1 Specification

Status: ready-for-agent

## Problem Statement

Developers working in single-model Antigravity sessions—such as frontier reasoning models selected directly in the IDE—lack the built-in two-phase planning and execution scheduling of the native Antigravity Orchestrator. Without that separation, every mechanical file edit, command run, test iteration, and multi-step implementation turn runs directly inside the primary session on the expensive frontier model, burning scarce quota, bloating the planning context window with raw tool output, and blurring architectural decision-making with execution trial-and-error. Conversely, naive delegation to generic subagents loses the living conversational context that native same-thread model hot-swapping preserves, risks recursive planning loops when shared or workspace agent rules propagate into child subagents, and risks execution-tier drift if conversational mentions alter the execution model.

## Solution

Deliver an `orchestrator` pure-skill plugin and standalone skill package optimized in V1 for Antigravity single-model sessions (while preserving cross-client pure-skill manifests and a modular Harness Adapter Seam for future extensions), keeping the Official Orchestrator system intact everywhere outside cross-session `Living Memory Window` transport. Following Matt Pocock's pure-skill plugin layout, installing or enabling `orchestrator` registers only the self-contained skill—with zero bundled plugin rules directory, zero startup hooks, and zero persistent sidecars—so manual `/orchestrator` remains continuously reachable without hijacking ordinary sessions. Automatic activation in Antigravity is opted into separately through a concise `<=1 KB` copyable snippet in shared engineering rules or workspace agent rules. Across both rule-adopted and manual sessions, **one uniform tier rule** governs Antigravity execution: the bound `Execution Subagent` defaults to and locks at `flash`, permitting `pro`, `flash_lite`, or `inherit` **only** when explicitly passed via `/orchestrator <tier>` on that user request cycle. Whenever a request requires workspace edits or external side effects, the `Trunk Session` investigates strictly read-only on the user's main model, authors an Official `<plan>`, synchronizes its compaction-bounded `Living Memory Window` via a zero-LLM Python standard-library CLI, and dispatches execution to its bound `Execution Subagent`. Every completion, ~30-turn checkpoint, or early hand-back returns Official Orchestrator's five-part `<report>` into the unmodified three-way `[plan review]` gate, while parallel `Isolated Subagents` invoked by other plugins or skills remain completely untouched.

## User Stories

1. As a developer on Antigravity who adopts `orchestrator` via shared engineering rules or workspace agent rules, I want two-phase Plan and Execute scheduling to engage automatically on qualifying top-level requests with the bound `Execution Subagent` locked to `flash` and zero conversational tier drift, so that automatic orchestration matches Official Orchestrator without unexpected model upgrades.
2. As a developer who installs and enables the `orchestrator` plugin without adopting it in shared or workspace rules, I want ordinary sessions to remain unmediated single-model conversations—enforced by an explicit activation-authority gate and literal `/orchestrator` trigger discipline—while keeping manual `/orchestrator` always available.
3. As a developer explicitly invoking `/orchestrator <tier>` (`pro`, `flash_lite`, or `inherit`), I want that execution tier scoped across the active user-request cycle (including its internal `[plan review]` continuations) and rotated back automatically to `flash` on the next new user message, so that temporary overrides neither break mid-task continuations nor leak into later turns.
4. As a developer already running inside Antigravity's native Orchestrator mode, I want `orchestrator` to detect exact lowercase `exit_plan_mode` or `enter_plan_mode` tools and yield unconditionally (even if `/orchestrator` is typed), so that native same-thread hot-swapping never collides with subagent orchestration.
5. As a developer spawning child subagents inside an Antigravity workspace whose shared or workspace agent rules propagate to children, I want session origin checked at `step 0` both from prompt framing and deterministically from disk transcript `step 0` records (`SKIP_SUBAGENT_SESSION`), so that compacted or workspace-inherited child subagents never recurse while `Trunk Session` `<report>` wakeups still enter `[plan review]` normally.
6. As a developer asking a pure question, requesting an explanation, or asking for a read-only review that modifies nothing, I want the `Trunk Session` to answer directly in logical Plan Mode without spawning an `Execution Subagent`, matching Official Orchestrator's Direct Answer Gate.
7. As a developer sending a small follow-up whose steps are already settled in conversation (applying an approved tweak, rerunning a command, fixing a typo), I want the `Trunk Session` to skip redundant investigation and dispatch a concise one-to-two-sentence `<plan>` immediately, matching Official Orchestrator's Depth Matching rule.
8. As a developer requesting a non-trivial feature or refactor, I want the `Trunk Session` to investigate strictly read-only, resolve every ambiguity upfront, and author a complete five-section `<plan>` (ordered steps, target symbols and locations, exact changes, verification commands and expected outputs, and pitfalls ending with a task-specific `Re-plan if:` list), so that the `Execution Subagent` never guesses design decisions.
9. As a developer asking to inspect or approve a plan before changes are made, I want the `Trunk Session` to present the plan and stop without spawning an `Execution Subagent`, matching Official Orchestrator's Approve-First Exception.
10. As a developer handing off a `<plan>` on Antigravity, I want a newly spawned `Execution Subagent` to inherit the `Trunk Session`'s active `Living Memory Window`—retaining compaction summaries, stripped user prompts, visible assistant replies, and prior `Execution Subagent` `<report>` blocks while isolating `Isolated Subagent` outputs, raw tool results, system noise, and private reasoning—inside a session-isolated scratch directory outside my git repository.
11. As a developer who edits, retries, or rewinds earlier turns in a conversation, I want the synchronization CLI to fold append-only logs by canonical `step_index`, detect prefix-digest or watermark regressions, and detect vanished bound subagents after post-flush active-turn rewinds, so that rewound sessions automatically rotate to a fresh `Execution Subagent`.
12. As a developer whose `Living Memory Window` contains large messages, truncated fields, or unbroken lines, I want companion full-log expansion resolved prior to extraction, stale pages cleared per sync, and complete rendered Markdown pages guaranteed strictly below `40,000` UTF-8 bytes (`len(rendered) < 40000`), falling back cleanly to line and valid UTF-8 code-point splits.
13. As a developer iterating across multiple execution turns within the same compaction epoch and tier, I want `RESUME_EXISTING` to stage `pending_sync` symmetrically with `SPAWN_NEW` and commit watermarks via `bind` only after `send_message` succeeds, exporting `(last_synced_step .. max_folded_step]` (or `delta_empty: true`) and providing an idempotent `reset` command if a bound subagent was killed or expired.
14. As a developer crossing a host context compaction boundary, I want any change in `checkpoint_step` to leave the previous `Execution Subagent` idle at zero token cost and spawn a fresh `Execution Subagent` seeded from `[latest CHECKPOINT .. max_folded_step]`.
15. As a developer running a frontier model in my `Trunk Session`, I want model offloading applied exclusively to the bound `Execution Subagent`, and if that execution model hits quota exhaustion or an error, I want the `Trunk Session` to inspect workspace status and native subagent logs and report to me rather than silently switching models.
16. As a developer delegating execution, I want the `Execution Subagent` to handle minor mechanical deviations autonomously (slightly moved target, obvious missing import, rerunning a flaky test once) while treating an initial failure plus one failed retry as "failed twice" that belongs back on the `Trunk Session`.
17. As a developer delegating a long `<plan>`, I want the `Execution Subagent` to self-count roughly 30 LLM turns per dispatch and pause with an interim five-part status `<report>`, matching Official Orchestrator's scheduled review cadence.
18. As a developer whose `<plan>` hits any of Official Orchestrator's five early hand-back conditions—step or verification failed twice, false plan assumption, unchosen approach decision, unrequested out-of-plan edits or work, or any sign listed in `Re-plan if:`—I want the `Execution Subagent` to stop immediately and return `<report>` without improvising.
19. As a developer receiving an `Execution Subagent` `<report>`, I want the `Trunk Session` in `[plan review]` to inspect state read-only without carrying out the plan itself and take Official Orchestrator's exact three-way exit (continue remaining steps, send a revised plan stating what to undo, what to do instead, and how to verify it, or report verified completion or stop to me).
20. As a developer diagnosing a subtle execution issue, I want the `Trunk Session` to read the host's native subagent trajectory log URI on demand only when raw command output is needed.
21. As a developer invoking other plugins or skills that spawn `Isolated Subagents` from the `Trunk Session`, I want `orchestrator` to leave them completely parallel and untouched—zero `Living Memory Window` injection and zero model overrides—while nested workers spawned inside an active `Execution Subagent` naturally inherit the execution model.
22. As a developer explicitly invoking `/swarm` in a conversation, I want `orchestrator` to yield for that active `/swarm` workflow (and `[swarm]` or `[board]` worker turns) without interfering.
23. As a maintainer planning future support for additional clients such as Claude Code or Codex, I want standard pure-skill plugin manifests and a modular Harness Adapter Seam separating core two-phase orchestration from Antigravity runtime bindings, so future client optimization extends cleanly without redesigning the package.
24. As a maintainer validating the repository, I want deterministic zero-dependency Python standard-library `unittest` suites covering both the synchronization CLI (`Seam 1`) and structural package contracts (`Seam 2`), paired with a separate Antigravity live smoke verification checklist.

## Implementation Decisions

### 1. Matt-Aligned Pure-Skill Layout, Activation Authority, and Unified Tier Rule
- Both the plugin identifier and skill identifier are `orchestrator`, structured identically to Matt Pocock's pure-skill plugin layout: a self-contained skill directory (skill instructions, synchronization CLI script, execution protocol reference, and harness adapter reference) enclosed by three root JSON manifests (Antigravity root plugin manifest, Claude Code plugin manifest, and single-plugin marketplace manifest), concise user documentation containing a `<=1 KB` copyable Antigravity adoption snippet, and Python standard-library `unittest` suites. There is **strictly zero** bundled plugin-root rules directory, zero `hooks` startup scripts, zero Codex-specific V1 manifests or interface metadata, zero separate `rule-adoption` contract document, and zero persistent sidecar processes.
- **Non-Spontaneous Model-Invocable Frontmatter**: The skill frontmatter omits human-only invocation blocks (`disable-model-invocation: true`) so shared or workspace Antigravity rules can invoke `orchestrator`, while its frontmatter description restricts loading strictly to literal `/orchestrator` invocation or explicit active Antigravity rule adoption (omitting `"or names orchestrator"` to prevent hijacking ordinary discussions that merely mention the noun).
- **Single Unified Tier Rule**: Across both rule-adopted and manual invocations, the bound `Execution Subagent` defaults to and locks at `flash` (ignoring conversational model mentions to prevent drift). Overrides (`pro`, `flash_lite`, `inherit`) are permitted **only** when passed explicitly via `/orchestrator <tier>` on that request, persist across internal `[plan review]` continuations of that request, and automatically rotate back to `flash` on the next new user message.

### 2. Prompt Precedence and Centralized 4-Step Skill Entry Gate
- **Prompt Precedence (Official Part 1)**: Where two-phase orchestration rules conflict with generic investigate-then-edit habits, two-phase orchestration wins; it **never** overrides safety guidelines, user instructions, or tool permissions.
- **Centralized Entry Gate**: All four runtime guards below live in one authoritative Entry Gate at the top of the skill instructions (and summarized crisply in the `<=1 KB` copyable rule snippet in user documentation):
  1. **Gate 0 — Activation Authority**: Verify either the user literally invoked `/orchestrator` (with optional tier argument) OR an active Antigravity shared or workspace agent rule explicitly adopted `orchestrator`. If neither holds (e.g., an unsolicited automatic skill load), abort immediately and respond normally as a single model.
  2. **Gate 1 — Unconditional Native Orchestrator Deference**: If exact lowercase `exit_plan_mode` or `enter_plan_mode` tools are declared in the toolset (distinct case-sensitively from Claude Code's `EnterPlanMode` and `ExitPlanMode`), yield **unconditionally** to Official Native Orchestrator—even if `/orchestrator` was manually invoked.
  3. **Gate 2 — Active Workflow Deference**: Yield silently to explicit `/swarm` tasks (or `[swarm]` or `[board]` `@<worker>` turns) and standalone explicit workflow-skill invocations when `/orchestrator` was not explicitly requested alongside them.
  4. **Gate 3 — Antigravity Session-Origin (`step 0`) Non-Recursion**: Activate only on human-initiated top-level sessions (`step 0` is `<USER_REQUEST>` or compaction summary `# User Requests`, and confirmed by CLI `step 0` transcript inspection—not returning `SKIP_SUBAGENT_SESSION`). Any session woken at `step 0` by an inter-agent `<SYSTEM_MESSAGE>` (`[Message] timestamp=... sender=<parent_uuid> ...`, `[swarm]`, `[board]`) or carrying `[EXECUTION SUBAGENT — SINGLE PHASE]` treats two-phase routing as a strict no-op and runs single-phase, while top-level `Trunk Session` mid-session `<report>` wakeups enter `[plan review]` normally.

### 3. Verbatim Official 9-Part Baseline Mapping and Execution Protocol
- **9-Part Structural Preservation**:
  - Official **Parts 1, 2, 4, 5, 6, and 7** are preserved verbatim for Planning, Execution, Scheduled Review, and Planner Review; Official **Part 3** (`exit_plan_mode`) is replaced by native subagent dispatch plus five-part `<report>` return; Official **Parts 8 and 9** govern Antigravity native subagents, untouched parallel `Isolated Subagents`, and compaction-bounded `Living Memory Window` logs.
- **Planning Turn (`Trunk Session` — Official Part 2)**:
  - Starts on every qualifying user message and every inbound `<report>` wakeup.
  - **Direct Answer Gate**: Answer directly in-session and stop whenever nothing needs to be done (pure questions, explanations, read-only reviews). Anything that edits files, mutates state, or causes external effects goes to the `Execution Subagent`, however small.
  - **Approve-First Exception**: If the user asked to see or approve the plan first, present it and stop.
  - **Depth Matching**: Settled small follow-ups skip investigation and dispatch a 1–2 sentence `<plan>` immediately; non-trivial tasks investigate strictly read-only (preferring non-mutating flags on observational `run_command` builds, tests, or queries) and author a complete five-section `<plan>...</plan>` containing ordered steps, exact target symbols and locations, exact changes, verification commands and expected outputs, and pitfalls ending with a task-specific `Re-plan if:` list.
- **Execution Turn (`Execution Subagent` — Official Parts 4, 5, 6)**:
  - Begins every spawn and continuation with `[EXECUTION SUBAGENT — SINGLE PHASE]` plus the verbatim Non-Override Safety Clause placed once inside the static execution envelope (not duplicated by the planner inside each `<plan>`).
  - Carries out the most recent `<plan>` in order without re-planning.
  - **Small Deviations (Official Part 5.2)**: Handles minor mechanical deviations autonomously (slightly moved target, obvious missing import, rerunning a flaky test **once**). First failed attempt belongs to the `Execution Subagent`; **the second belongs to the `Trunk Session`** (initial failure plus one failed retry equals "failed twice").
  - **Five Early Hand-Back Triggers (Official Part 5.3 Verbatim)**: Stop immediately and return `<report>` whenever:
    1. A verification or step specified by the plan has failed twice;
    2. Something the plan assumed is missing or behaves differently;
    3. Continuing requires choosing between approaches the plan did not choose;
    4. Continuing requires editing files or doing work the plan did not name;
    5. Any sign in the plan's own `Re-plan if:` list appears.
  - **Scheduled Review Cadence (Official Part 6)**: Self-counts LLM execution turns per dispatch and pauses after ~30 execution turns to return an interim five-part status `<report>`.

### 4. Parallel Orthogonality with Isolated Subagents
- `Execution Subagent` and plugin or skill `Isolated Subagents` operate as parallel, independent channels from the `Trunk Session`: `orchestrator` applies `Living Memory Window` synchronization and `flash`-default tier control **solely** to its single bound `Execution Subagent`, imposing zero memory injection, zero model overrides, and zero special-case routing on `Isolated Subagents`.
- Nested subagents spawned from inside an active `Execution Subagent` (`depth = 1`) naturally inherit the execution model via `inherit`; if a runtime environment disables nested subagent tools inside a child subagent, Trigger #2 hands back cleanly to the `Trunk Session`.

### 5. Deterministic Antigravity Living Memory Synchronization CLI Contract
- Implemented using only the Python 3 standard library (`py -3` on Windows or `python3` on POSIX, invoked via its exact path relative to the skill directory).
- **Runtime Path Resolution**: Given the active session's `<Artifact Directory Path>`, `--transcript` resolves to the session's primary system-generated transcript log inside that artifact directory (with its fixed companion full-log file in the same logs directory), and `--state-dir` resolves to the session-isolated `orchestrator` scratch subdirectory inside that artifact directory.
- **CLI Subcommands & Exit Codes** (override `ArgumentParser` error exit to return **`1`** on bad CLI arguments rather than Python's default `2`):
  - `0` = success; `1` = invalid CLI arguments, invalid JSON state, or `bind` called when `pending_sync` is `null`; `2` = missing conversation artifact logs parent directory, unreadable transcript, or corrupt non-JSON mid-file records.
  - **Turn-1 Missing/Empty Transcript Grace**: If the logs parent directory exists on Turn 1 while the primary transcript file does not yet exist or is 0 bytes, `sync` returns clean initial `SPAWN_NEW` (`checkpoint_step: -1`, `synced_through: -1`, `prefix_digest: ""`, `delta_empty: true`, `pages: []`, exit `0`).
  1. `sync --transcript <path> --state-dir <dir> [--tier <str>]` (default `--tier flash`):
     - **Canonical Folding**: Folds append-only JSONL records by integer `step_index` (a later record at `k` invalidates earlier records at `>= k`, gracefully ignoring a truncated incomplete partial line at EOF).
     - **Hard `step 0` Backstop**: If folded `step 0` exists and has `type == "SYSTEM_MESSAGE"`, exits `0` immediately emitting `{"action": "SKIP_SUBAGENT_SESSION", "tier": "<tier>", "subagent_id": null, "checkpoint_step": -1, "synced_through": -1, "prefix_digest": "", "delta_empty": true, "pages": []}` without mutating state.
     - **Pre-Extraction Truncation Resolution**: Before extracting or regex-matching text within the retained window, expands any retained step whose `truncated_fields` includes `"content"` from the fixed sibling companion full-log file (matching same 0-based JSONL line index first, then last matching `(step_index, type)` record; falling back gracefully to compact `content` with exit `0` if the companion file is absent).
     - **Positive Window Extraction `[max(0, latest_checkpoint_step) .. max_folded_step]`** (`latest_checkpoint_step = -1` when no `CHECKPOINT` exists):
       - `CHECKPOINT`: full `content` compaction summary;
       - `USER_INPUT`: strip `<ADDITIONAL_METADATA>...</ADDITIONAL_METADATA>` and `<USER_SETTINGS_CHANGE>...</USER_SETTINGS_CHANGE>` first, then unwrap only the **outermost** `<USER_REQUEST>...</USER_REQUEST>` envelope (preserving any inner literal tags; falling back to stripped text if tags are absent);
       - `PLANNER_RESPONSE`: non-empty string `content` (ignoring `thinking`, `tool_calls`, `GENERIC`, and `ERROR_MESSAGE`);
       - `SYSTEM_MESSAGE` or `EPHEMERAL_MESSAGE`: extract `<report>...</report>` blocks **strictly** when `[Message] ... sender=<id>` matches `<id>` in `state.execution_subagent_ids`, ignoring all non-report messages and any other sender UUIDs.
     - **Pagination**: Clears stale page files in the state directory's pages subdirectory before rendering sequential Markdown page files (`page_001`, `page_002`, ...) whose **total rendered UTF-8 byte length including page headers and message separators** strictly satisfies `len(rendered_bytes) < 40000`, splitting progressively on message boundaries, line boundaries, and valid UTF-8 code-point boundaries.
     - **Session State JSON Schema**:
       ```text
       {
         "bound_subagent_id": str | null,
         "bound_tier": str,
         "execution_subagent_ids": list[str],
         "checkpoint_step": int,
         "last_synced_step": int,
         "prefix_digest": str,
         "pending_sync": {
           "tier": str,
           "checkpoint_step": int,
           "synced_through": int,
           "prefix_digest": str,
           "reset_history": bool
         } | null
       }
       ```
       where initial sentinel values before first `bind` are `bound_subagent_id: null`, `checkpoint_step: -1`, `last_synced_step: -1`, `prefix_digest: ""`, `execution_subagent_ids: []`, and `prefix_digest` is the `sha256` hex digest of canonical JSON `(step_index, type, extracted_text)` tuples across folded records `[0 .. last_synced_step]`.
     - **Symmetric Two-Phase Watermark Decision**: Neither `SPAWN_NEW` nor `RESUME_EXISTING` mutates active watermarks inside `sync`—both stage `pending_sync` until `bind`. `sync` emits `SPAWN_NEW` (`subagent_id: null`) whenever `bound_subagent_id` is `null`, `latest_checkpoint_step != checkpoint_step`, `max_folded_step < last_synced_step`, folded prefix digest through `last_synced_step` differs from `prefix_digest`, `bound_subagent_id` is absent from all folded `GENERIC` and `SYSTEM_MESSAGE` records in `[max(0, latest_checkpoint_step) .. max_folded_step]` (catching post-flush active-turn rewinds), or `tier != bound_tier` (exporting the full active epoch). Otherwise `sync` emits `RESUME_EXISTING` (`subagent_id: bound_subagent_id`), exporting `(last_synced_step .. max_folded_step]` (or `delta_empty: true`, `pages: []`).
     - **Stdout JSON Schema (Single Line)**:
       `{"action": "SPAWN_NEW" | "RESUME_EXISTING" | "SKIP_SUBAGENT_SESSION", "tier": "<str>", "subagent_id": "<str>|null", "checkpoint_step": <int>, "synced_through": <int>, "prefix_digest": "<hex>", "delta_empty": <bool>, "pages": ["<abs_path>", ...]}`
  2. `bind --state-dir <dir> --subagent-id <id>`: Promotes `pending_sync` + `subagent_id` into active state immediately after `invoke_subagent` (on `SPAWN_NEW`) or `send_message` (on `RESUME_EXISTING`) succeeds, resets `execution_subagent_ids` to `[id]` when `pending_sync.reset_history` is true (`CHECKPOINT` change, rewind, or initial spawn) and otherwise ensures `<id>` is present, clears `pending_sync = null`, and prints `{"status": "bound", "subagent_id": "<id>"}`.
  3. `reset --state-dir <dir>`: Idempotently clears session state and exported pages (succeeding even if state does not yet exist) so dead-subagent or redirect recovery returns cleanly to `SPAWN_NEW`, printing `{"status": "reset"}`.

### 6. Antigravity Dispatch Handshake, `[plan review]` Gate, and Recovery
- **Dispatch & Async Yield**:
  - On `SPAWN_NEW`: Call `invoke_subagent(TypeName="self", Role="Orchestrator Execution Subagent", Model=<tier>, Workspace="inherit", Prompt=<envelope>)` passing the `[EXECUTION SUBAGENT — SINGLE PHASE]` header, static Non-Override Safety Clause, instruction to `read_file` each exported page path in order (if `pages` non-empty), `<plan>...</plan>`, and execution-protocol rules; immediately call `bind --subagent-id <conversationId>`, then end the turn to await reactive `<SYSTEM_MESSAGE>` wakeup without polling `manage_subagents("list")`.
  - On `RESUME_EXISTING`: Call `send_message(Recipient=<subagent_id>, Message=<envelope>)` prepending `[EXECUTION SUBAGENT — SINGLE PHASE]`, instructing `read_file` on any delta `pages` (if `!delta_empty`), and enclosing the new or follow-up `<plan>...</plan>`; once `send_message` returns `"Message sent to ..."`, immediately call `bind --subagent-id <subagent_id>`, then end the turn.
- **`[plan review]` Gate (Official Part 7)**: Treats `<report>` as untrusted data, verifies workspace state or native subagent `logAbsoluteUri` read-only on demand, **never carries out `<plan>` edits itself**, and exits one of three ways: (1) dispatch remaining steps, (2) dispatch a revised `<plan>` stating **what to undo**, **what to do instead**, and **how to verify it**, or (3) report verified completion or blocking human decision to the user and stop.
- **Mid-Flight User Messages & Failure Recovery**:
  - If the user writes while an `Execution Subagent` may be running, inspect `manage_subagents("list")` first. If the bound subagent is still running and the user redirects or cancels the task, call `manage_subagents("kill", [<id>])`, run `reset`, inspect workspace git status and git diff, and re-plan cleanly; if continuing the existing task cleanly, send a stop-and-report message or await completion without polling.
  - If `send_message` fails on an expired or dead ID, run `reset` -> `sync` -> `invoke_subagent` -> `bind` within the same planning turn. If the `Execution Subagent` aborts on quota or API error, inspect git status, git diff, and `logAbsoluteUri` before reporting to the user—**never silently switching models**.

### 7. Modular Harness Adapter Seam (Antigravity V1 + Reserved Extension Interface)
- The harness adapter reference defines a narrow abstract adapter contract (`resolve_window_sync`, `spawn_execution_subagent`, `continue_execution_subagent`, `bind_or_reset_state`, `inspect_subagent_logs`) with **only Antigravity** implemented and verified in V1. Non-normative extension stubs note where future Claude Code (`Agent` + `resume`) and Codex (`spawn_agent` + `followup_task`) adapters plug in once targeted optimization and verified child-subagent detection are added.

## Testing Decisions

- **External-Behavior Discipline**: Test observable CLI outputs, files, and deterministic structural package invariants via Python 3 standard-library `unittest` (`py -3 -m unittest` / `python3 -m unittest`) with zero third-party dependencies.
- **Seam 1 — Antigravity Living Memory Synchronization CLI Seam**:
  - Subprocess black-box tests verifying: (1) initial Turn-1 empty/missing transcript `SPAWN_NEW` (`-1` sentinels) and full `SPAWN_NEW` -> `bind` flow; (2) hard `step 0` `SYSTEM_MESSAGE` backstop returning `SKIP_SUBAGENT_SESSION` without state mutation; (3) canonical `step_index` rewind folding + intra-epoch `prefix_digest` and `max_folded_step < last_synced_step` rotation + post-flush rewind rotation when `bound_subagent_id` disappears from folded records + pre-extraction companion full-log resolution and graceful missing-companion fallback; (4) outermost `<USER_REQUEST>` unwrap with embedded literal `</USER_REQUEST>` preservation and `sender in execution_subagent_ids` `<report>` isolation across tier rotations; (5) total rendered Markdown page size strictly `< 40,000` UTF-8 bytes including headers and separators, single unbroken multi-byte line splitting, and stale-page cleanup; (6) symmetric two-phase `RESUME_EXISTING` (verifying un-bound `sync` does not advance `last_synced_step` and loses zero deltas), `delta_empty: true` elision, `tier != bound_tier` rotation, idempotent `reset`, `CHECKPOINT` epoch rotation, and exit codes `1` (bad CLI args via `ArgumentParser` override, bad JSON state, `bind` without `pending_sync`) and `2` (missing logs parent dir, corrupt mid-file JSONL).
- **Seam 2A — Automated Package Contract Suite (Deterministic `unittest`)**:
  - Validates: all 3 root manifests (`Antigravity root`, `Claude Code plugin`, `single-plugin marketplace`) are valid JSON under unified `orchestrator` naming; **strict absence** of any bundled plugin-root rules directory, hooks configuration, Codex-only V1 manifests, or separate `rule-adoption` contract file; valid skill frontmatter permitting model invocation (no `disable-model-invocation: true`) while omitting `"names orchestrator"`; user documentation contains the `<=1 KB` Antigravity rule snippet; all relative links between skill instructions and script or reference modules resolve cleanly on disk; and zero CJK characters appear across all tracked text files.
- **Seam 2B — Antigravity Live Smoke Verification Checklist (Manual Post-Build Verification)**:
  - Verify live Antigravity trajectories for: (1) unconditional deference to exact lowercase `exit_plan_mode`/`enter_plan_mode` (even when `/orchestrator` is manually typed); (2) `step 0` child-subagent single-phase non-recursion across both live and post-compaction turns under inherited workspace rules; (3) `flash` lock under shared-rule adoption (ignoring conversational tier mentions) vs `/orchestrator <tier>` request-scoped override and automatic return to `flash` on the next user turn; and (4) parallel `Isolated Subagents` remaining completely untouched with zero memory injection or model overrides.
- **Prior Art**: Empirical Antigravity SQLite and JSONL trajectory probes (`Probes A, B, C` and `L0-1` payload benchmarks) and behavioral skill pressure-testing (`writing-skills`).

## Out of Scope

- Targeted runtime optimization, living-memory transcript adapters, and automatic-rule subagent non-recursion for non-Antigravity clients (Claude Code, Codex), beyond preserving multi-client manifest compatibility and adapter interface stubs.
- Bundling plugin-root rules, startup shell hooks, Codex plugin manifests, or persistent UI sidecar panels.
- Maintaining a parallel `swarm`-based execution carrier alongside point-to-point native subagents.
- External headless CLI subprocess orchestration or LLM-generated conversation summaries.
- Custom disk receipt schemas or error dump files duplicating host trajectory logs.
- Connecting or pushing the repository to a remote GitHub host before local V1 verification completes and the user explicitly requests it.
