# Coexistence Boundaries and Parallel Orthogonality with Isolated Subagents

To coexist cleanly with native Orchestrator sessions, prevent recursive Plan/Execute loops inside child subagents, and avoid Official Orchestrator's same-thread temporal coupling between execution offloading and plugin/skill subagents, we enforce three orthogonal boundaries inside Antigravity rule-adoption guidance and `SKILL.md`'s centralized Entry Gate: (1) when exact lowercase `exit_plan_mode` or `enter_plan_mode` is declared in the session toolset, `orchestrator` yields **unconditionally** to Official Native Orchestrator (even if the user manually invoked `/orchestrator`), and yields silently whenever the user explicitly invokes `/swarm` (or during `[swarm]`/`[board]` `@<worker>` turns); (2) Antigravity rule-driven activation and `SKILL.md`'s Entry Gate check **session origin (`step 0`)** first via live prompt framing with zero CLI calls on ordinary Q&A turns (human `<USER_REQUEST>` vs `[Message] timestamp=... sender=<parent_uuid> ...`, `[swarm]`/`[board]` `@<member>`, or `[EXECUTION SUBAGENT — SINGLE PHASE]`), calling read-only `sync_memory.py check-origin` in Gate 3 **only** when resuming from context compaction (`# Resuming from a compaction`) while relying on `sync_memory.py sync`'s `SKIP_SUBAGENT_SESSION` backstop before subagent dispatch, guaranteeing compacted or workspace-inherited child subagents always run single-phase while `Trunk Session` `<report>` wakeups enter `[plan review]` normally; and (3) `Execution Subagent` and `Isolated Subagents` operate as parallel, independent channels from the `Trunk Session`—`Living Memory Window` synchronization and default `flash` offloading apply solely to the single bound `Execution Subagent`, whereas all `Isolated Subagents` invoked by plugins or skills (`egm-*`, `code-review`, `research`, etc.) receive zero `Living Memory Window` injection and retain 100% of their own native skill/client model rules and explicit user parameters without special-case routing inside `orchestrator` (with only nested workers spawned from inside an active `Execution Subagent` naturally inheriting the execution model via `inherit`, or handing back via Trigger #2 if nested tools are unavailable).
