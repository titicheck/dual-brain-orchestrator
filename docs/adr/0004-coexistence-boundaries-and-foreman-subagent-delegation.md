# Coexistence Boundaries and Parallel Orthogonality with Isolated Subagents

To coexist cleanly with native Orchestrator sessions, prevent recursive Plan/Execute loops inside child subagents, and avoid Official Orchestrator's same-thread temporal coupling between execution offloading and plugin/skill subagents, we enforce three orthogonal boundaries inside Antigravity rule-adoption guidance and `SKILL.md`'s centralized Entry Gate: (1) when exact lowercase `exit_plan_mode` or `enter_plan_mode` is declared in the session toolset, `orchestrator` yields **unconditionally** to Official Native Orchestrator (even if the user manually invoked `/orchestrator`), and yields silently whenever the user explicitly invokes `/swarm` (or during `[swarm]`/`[board]` `@<worker>` turns); (2) Antigravity rule-driven activation and `SKILL.md`'s Entry Gate check **conversation root origin (`step 0`)**—always invoking read-only `sync_memory.py check-origin` first when `# Resuming from a compaction` appears (even if an inbound `[Message]` is also on that turn) and failing closed on `"SUBAGENT"` or `"UNKNOWN"`, while on uncompacted conversations yielding as single-phase **only** when the conversation's initial root turn started with `[Message] timestamp=... sender=<parent_uuid>` (no preceding `<USER_REQUEST>` turns), `[swarm]`, `[board]`, or `[EXECUTION SUBAGENT — SINGLE PHASE]`, reinforced by `sync_memory.py sync`'s `SKIP_SUBAGENT_SESSION` backstop before dispatch so child subagents inheriting `AGENTS.md` always run single-phase while `Trunk Session`s woken mid-conversation by `Execution Subagents`, `Isolated Subagents` (`research`, `egm-*`, `code-review`), or orphaned subagents remain `Trunk Session`s; and (3) `Execution Subagent` and `Isolated Subagents` operate as parallel, independent channels from the `Trunk Session`—`Living Memory Window` synchronization and `orchestrator-tier:` offloading apply solely to the single bound `Execution Subagent`, whereas all `Isolated Subagents` invoked by plugins or skills receive zero `Living Memory Window` injection and retain 100% of their own native skill/client model rules and explicit user parameters without special-case routing inside `orchestrator` (with only nested workers spawned from inside an active `Execution Subagent` naturally inheriting the execution model via `inherit`, or handing back via Trigger #2 if nested tools are unavailable).
