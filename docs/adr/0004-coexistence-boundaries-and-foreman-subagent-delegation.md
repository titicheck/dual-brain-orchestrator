# Coexistence Boundaries and Parallel Orthogonality with Isolated Subagents

To coexist cleanly with native Orchestrator sessions, prevent recursive Plan/Execute loops inside child subagents, and avoid Official Orchestrator's same-thread temporal coupling between execution offloading and plugin/skill subagents, we enforce three orthogonal boundaries inside Antigravity rule-adoption guidance and `SKILL.md`'s centralized Entry Gate: (1) when exact lowercase `exit_plan_mode` or `enter_plan_mode` is declared in the session toolset, `orchestrator` yields **unconditionally** to Official Native Orchestrator (even if the user manually invoked `/orchestrator`), and yields likewise whenever `/swarm` or another standalone workflow-owning skill without `/orchestrator` is invoked for the active task; (2) Antigravity rule-driven activation and `SKILL.md`'s Entry Gate check **session origin (`step 0`)** both in prompt framing (human `<USER_REQUEST>` or compaction summary `# User Requests` vs `[Message] timestamp=... sender=<parent_uuid> ...`, `[swarm]`/`[board]` `@<member>`, or `[EXECUTION SUBAGENT — SINGLE PHASE]`) and deterministically via `sync_memory.py` reading folded `step 0` from `transcript.jsonl` (`SKIP_SUBAGENT_SESSION`), guaranteeing child subagents inheriting shared/workspace `AGENTS.md` always run single-phase even across context compactions while `Trunk Session` `<report>` wakeups enter `[plan review]` normally; and (3) `Execution Subagent` and `Isolated Subagents` operate as parallel, independent channels from the `Trunk Session`—`Living Memory Window` synchronization and default `flash` offloading apply solely to the single bound `Execution Subagent`, whereas all `Isolated Subagents` invoked by plugins or skills (`egm-*`, `code-review`, `research`, etc.) receive zero `Living Memory Window` injection and retain 100% of their own native skill/client model rules and explicit user parameters without special-case routing inside `orchestrator` (with only nested workers spawned from inside an active `Execution Subagent` naturally inheriting the execution model via `inherit`, or handing back via Trigger #2 if nested tools are unavailable).
